## A. 旧 Hybrid 为什么退化

旧评测中的 “Hybrid” 来自 `scripts/10_eval_retrieval.py` 的 `search_hybrid`，现已更名为 `search_hybrid_legacy_union_safe`。它**既不是 RRF，也不是加权融合**，而是 v0.3.2 的 union_safe 规则：

1. 取 BM25 top-5 与 Dense top-5 的并集，再加上两路 top-25 中的其余候选，去重；
2. 按 `(bm25_rank or 999, dense_rank or 999)` 排序。

它不使用任何分数。配置里的 0.45 / 0.55 权重从未生效。

已证实的缺陷（v0.9 诊断）：

| # | 缺陷 | fixed_39 上的证据 |
|---|---|---|
| 1 | 以 BM25 名次为主键，Dense 只在名次相同时起作用 | 19/39 题的 top-10 与 BM25 top-10 完全相同；与 BM25 top-10 平均重叠 9.18 个，与 Dense top-10 平均重叠 2.54 个 |
| 2 | 名次标注丢失：在 Dense 循环中先加入的候选只记 `dense_rank`。即使它也在 BM25 top-25 中，仍按 999 排到所有 BM25 候选之后，于是两路都认为相关的候选反而排在最后 | 发生 86 次，其中 21 次是证据 Chunk；按这条规则独立重算，39/39 题与旧结果一致 |
| 3 | 只出现在 Dense 中的候选记为 999，在 top-10 截断时基本被丢掉 | Dense top-5 中有 142 个 Chunk 没进入旧 Hybrid 的 top-10，其中 22 个是证据 |
| 4 | 不过滤零分 BM25 候选，并且会修改输入字典（副作用） | 在本数据上未观察到对结果的影响 |

结果：旧 Hybrid 相对单独的 BM25 **改善 0 题、退化 6 题**（按完成名次比较）。

### 如何用单元测试复现

`ragas_eval/tests/test_v12_legacy_and_config.py::TestLegacyUnionSafeDefects` 用合成排名复现了上述机制，不需要模型和语料：

- 一个 Chunk 在 BM25 排第 6、在 Dense 排第 1。它在旧 Hybrid 中被排到 BM25 第 25 名之后，进不了 top-10（缺陷 2）；
- 只出现在 Dense 中的候选进不了 top-10（缺陷 3）；
- 旧 Hybrid 的 top-10 与 BM25 顺序完全相同（缺陷 1）；
- 同样的输入交给 `rrf_fuse`，两路都有的 Chunk 排第 1，Dense 独有的候选也进入 top-10。

### 修复后的固定题集 A/B

在同一个 fixed_39、同一索引、同一候选池下比较以下策略，策略和参数都在看结果之前固定：

- A：Dense
- B：BM25
- C：旧 Hybrid（union_safe，原样保留）
- D：RRF（k=60，候选池 25/25）
- E：修正后的加权融合（0.45/0.55）

另有三个 E 的权重变体，是在同一测试集上挑选的，只作探索性参考，不作为结论。

为确认基线可复现，A/B/C/D 四个策略的 top-10 都与 v0.8.2 的机器评估结果逐题一致（各 39/39）。

控制变量：五个策略使用同一题集（fixed_39，题集与 GT 文件哈希记录在研究项目的实验清单中）、同一语料版本与索引文件、同一 Embedding 模型版本、同一 top-K=10 和同一候选池大小（25）。唯一变化的是融合方式。

## B. Dense 与 RRF 比较（fixed_39）

| 指标 | A Dense | B BM25 | C 旧 Hybrid（legacy） | D RRF |
|---|---|---|---|---|
| Hit@3 / @5 / @10 | 0.7949 / 0.9231 / 1.0 | 0.5897 / 0.7436 / 0.8974 | 0.5897 / 0.7436 / 0.8205 | 0.8718 / 0.9487 / 0.9744 |
| Recall@3 / @5 / @10 | 0.75 / 0.8718 / 0.9487 | 0.5406 / 0.6688 / 0.8312 | 0.5406 / 0.6688 / 0.7094 | 0.7885 / 0.906 / 0.938 |
| MRR | 0.759 | 0.5539 | 0.5431 | 0.7772 |
| FullCov@3 / @5 / @10 | 0.6923 / 0.8205 / 0.8974 | 0.5128 / 0.6154 / 0.7436 | 0.5128 / 0.6154 / 0.6154 | 0.6923 / 0.8462 / 0.8718 |
| 组合 FullCov@3 / @5 / @10 | 0.7179 / 0.8462 / 0.9231 | 0.5128 / 0.6154 / 0.7692 | 0.5128 / 0.6154 / 0.6154 | 0.6923 / 0.8718 / 0.8974 |

指标说明（与研究代码一致）：

- **Recall@K**：对每个“充分证据集合”，计算 top-K 覆盖的比例，取各集合中的最大值。这是 Chunk 级的召回，不是旧的 Source Hit。
- **FullCov@K**：至少一个充分集合被 top-K 完整覆盖。
- **组合 FullCov@K**：按“证据槽”判断（证据槽之间为 AND，同一槽内的备选组之间为 OR），所有证据槽都被 top-K 覆盖才算完整。
- **MRR**：第一个证据 Chunk 名次的倒数（只看 top-10）。

逐题完成名次（所有证据槽都被覆盖时的最小 K，未完成记为 11）：

| 比较 | 改善 | 退化 | 不变 |
|---|---|---|---|
| D RRF 相对 A Dense | 10 | 8 | 21 |
| D RRF 相对 C 旧 Hybrid | 20 | 0 | 19 |
| C 旧 Hybrid 相对 B BM25 | 0 | 6 | 33 |

其中 “D 相对 A” 和 “C 相对 B” 两行，是根据研究项目逐题比较表中的完成名次计算得出的。

按题型拆分（v0.9.1 复现，B_rrf 即上表的 D）：

- 单文档 34 题：RRF 的 FullCov@5 为 0.9412，Dense 为 0.9118。
- 跨文档 5 题：两者的 FullCov@10 都只有 0.2–0.4，组合 FullCov@10 分别为 0.4（RRF）和 0.6（Dense）。

由此可见，跨文档的证据整合是两种方法共同的短板。

**结论与取舍**：RRF 的 Hit@3/5、Recall@3/5、MRR 和 FullCov@5 高于 Dense；Dense 的 Hit@10、Recall@10 和 FullCov@10 更高。两者逐题互有胜负（改善 10、退化 8）。考虑到生成只使用 top-5 上下文，以及下文的端到端结果，正式服务选择了 RRF。修正后的加权融合（E）与 RRF 相近，没有被采用。

## v0.9.1：多证据扩展实验（未采用）

查询分解（C/D）、多样性重排（E/F）和查询分解加 RRF 都试过，都没有带来净收益：

- D_decomp_rrf 相对 B_rrf：改善 4、退化 5；
- F_rrf_diverse 相对 B_rrf：改善 1、退化 9。

查询分解还会让检索耗时翻倍：平均端到端约 214 ms，而 RRF 约 113 ms。因此这些方法都没有接入正式服务。

holdout_6 的 6 道题与 fixed_39 的知识点重复，不能作为独立的泛化验证。
