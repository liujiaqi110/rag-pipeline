## A. AI 应用工程师方向

**企业知识库管理平台：带 ACL 的本地 RAG 系统**（个人项目 · Python / FastAPI / Vue 3 / Ollama）

**项目简介**：在本机离线运行的企业知识库平台，覆盖文档上传与自动索引、按部门 / 角色 / 用户授权的检索问答、SSE 流式回答、FAQ 自动沉淀、知识缺口闭环和运营看板。共 5 个开发阶段，全部用自动化测试和真实浏览器端到端测试验收。

**主要工作**：

- **端到端 RAG 架构**：
  - 文档解析（MD / TXT / PDF / DOCX）→ 清洗 → 结构化切片（复用原有切片脚本，有测试证明结果与批处理脚本逐条一致）→ 写入新的 BM25 + bge-m3 Dense 索引代际，回读校验后原子激活。
  - 检索用 RRF 融合（k=60，候选池 25/25）；本地 Ollama qwen2.5:7b 生成；SSE 流式输出。
- **检索阶段的权限控制**：设计文档级 ACL（默认拒绝、拒绝优先、密级与授权同时满足，没有超级用户），在 BM25 / Dense / RRF 的**候选阶段**过滤无权 Chunk，而不是在 top-5 结果上过滤。
  - 用 30 个高度相关的机密 Chunk 构造测试：如果只过滤 top-5，授权用户会拿不到任何上下文；改为候选阶段过滤后，能拿到完整的 top-5。
  - 加上 Prompt 闸门、输出 ID 脱敏，无权文档与不存在的文档返回相同的 404。
- **安全与一致性**：
  - JWT 的 jti 存在服务端，登出、停用、权限变更后 Token 立即失效；防住了 alg=none、伪造 jti 等攻击（有测试）。
  - 生成过程中每 0.5 秒重新校验 Token 和权限，撤权或登出时中断流式输出。
  - 答案缓存键包含用户权限指纹和索引代际；引用固定到回答时的文档版本。
  - 自己做安全回归时发现并修复了 3 个可复现问题（流式片段 ID 屏蔽比最终校验宽松、引用没有固定版本、权限受限被误记为知识缺口），每个问题都先写出修复前失败的测试。
- **FAQ 自动挖掘与缓存**：基于真实问答做 bge-m3 语义聚类，按证据文档集合拆分，候选答案只能基于证据文档生成。
  - 审核状态机：候选 → 发布 / 驳回，已发布 ↔ 下线；挖掘从不自动发布，审核人必须能阅读全部证据文档。
  - FAQ 命中时不调用模型。权限、文档版本、索引代际或下线状态变化时立即失效（全员 / 部门 / 角色 / 个人四类 FAQ 都有测试）。
  - 在一次合成数据的端到端运行中：FAQ 命中的服务端延迟为 145–157 ms，同一次运行中模型生成耗时 415–3240 ms。
- **工程化**：
  - FastAPI + SQLAlchemy + Alembic：4 个迁移版本，用冻结的旧版表结构验证“原地升级、数据保留”；修复了 SQLite batch 迁移中外键级联导致数据丢失的隐患。
  - 文档解析、Embedding、建索引改为可查询进度、可取消、可重试的后台任务；构建失败时旧索引不受影响。
  - Vue 3 + TypeScript + Element Plus 工作台，统一设计 Token。
- **测试、CI 与可观测性**：
  - 后端 114 个、RAG / ACL 102 个、前端 17 个自动化测试；2 个 Playwright 浏览器端到端场景（真实后端 + 本地模型 + 合成数据）。
  - GitHub Actions 在没有模型和凭据的环境中运行后端、检索评估和前端测试。
  - 每个问题写一行服务日志，区分 FAQ 命中、答案缓存、RAG、权限受限、模型失败、基础设施故障；运营看板展示 Token、P50/P95、FAQ 命中率、知识缺口，每个指标都有明确口径。

**技术栈**：Python 3.12 · FastAPI · SQLAlchemy · Alembic · PyJWT · BM25 · sentence-transformers / bge-m3 · Ollama / qwen2.5:7b · Vue 3 · TypeScript · Pinia · Element Plus · ECharts · Vitest · Playwright · GitHub Actions

## B. 大模型算法工程师方向

**本地 RAG 检索融合优化与企业级权限约束检索**（个人项目 · Python / bge-m3 / Ollama）

**项目简介**：围绕中文本地 RAG 的检索融合、引用安全和可复现评估做研究；在此基础上扩展为带 ACL 的企业知识库，在**权限约束下**做检索、FAQ 语义聚类和知识缺口识别。

**主要工作**：

- **检索融合缺陷定位与修复**：发现原有的 union_safe Hybrid（以 BM25 排名为主的并集）存在排序退化：在 39 道题上，FullCov@10 只有 0.6154，低于单独用 BM25 的 0.7436（相对 BM25 退化 6 题、改善 0 题）。
  - 改用 RRF（k=60，候选池 25/25，只融合排名，不混合原始分数）后，相对旧 Hybrid 改善 20 题、退化 0 题；MRR 为 0.7772（Dense 0.759，旧 Hybrid 0.5431）。
  - RRF 与 Dense 互有胜负：FullCov@5 为 0.8462 对 0.8205，FullCov@10 为 0.8718 对 0.8974（逐题看改善 10、退化 8）。最终选 RRF 作为服务默认策略。
- **端到端评估与回归门禁**：在本地 qwen2.5:7b 上做了 96 次真实生成，自动评判结果：回答正确 RRF 24/39、Dense 20/39；无答案题正确拒答 RRF 7/8、Dense 4/8。
  - 新 Prompt rag_v1.1 因为新增可答题误拒和模板泄漏，没有通过回归门禁，因此没有采用。
  - 所有结果都标记为 automated / provisional，并说明研究版 Recall（取各证据集合中的最大覆盖）与示例版 Recall（取证据并集）口径不同、不能横向比较。
- **引用安全层**：引用 ID 精确校验（拦截截短、加长、伪造的 ID）、完全拒答时清除引用、来源归属保护。在 260 条历史输出上离线回归：11 条无效引用全部被拦截（其中 4 条是旧校验漏掉的），合法引用误删 0 条。
- **权限约束下的检索**：在 BM25 打分和 Dense 候选池填充阶段只考虑授权 Chunk。保留全库 IDF，使授权 Chunk 的分数与无 ACL 时完全一致；用“有权限时与无 ACL 时结果逐条相同”的等价测试，证明没有改变原有排序行为。
- **语义聚类与知识缺口**：
  - 用 bge-m3 归一化向量做贪心质心聚类，频次和相似度阈值可配置；按证据文档集合拆分，避免把基于不同权限文档的回答合并成同一条 FAQ。
  - 在一次真实端到端运行中，3 个同义问题的簇内平均相似度为 0.971。
  - 知识缺口分为无证据、检索相关性不足（授权范围内最佳 Dense 相似度低于阈值）、证据不足、知识过期四类。
  - 比较“全库最佳证据”与“授权范围内最佳证据”，把“答案只在无权文档中”识别为权限受限而不是缺口。
- **可复现与本地部署**：离线运行 bge-m3（不自动下载）与 Ollama；切片、建索引、评估都可复现（示例集评估结果与已提交的数据完全一致）；需要真实模型的集成测试与 CI 分开运行。

**技术栈**：bge-m3 · sentence-transformers · BM25 · RRF · Ollama / qwen2.5:7b · numpy · 检索评估（Recall@K / FullCov@K / MRR / nDCG）· Python unittest · FastAPI

**可以如实说明的局限**：问答质量评估没有独立的人工验证集；示例语料规模很小，指标接近饱和；FAQ 匹配和聚类阈值只在合成数据和 bge-m3 上验证过；P6 模型微调尚未开始。
